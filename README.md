# meta-helium

Experimental **Torizon OS 8** support for the **PCB Arts Helium**
(Jetson Orin NX 16GB, `HOX2-D1-V5`). This is not an official Toradex BSP.

| | |
|---|---|
| Machine | `helium-orin-nx` |
| Distro | `common-torizon` (Torizon OS 8, Yocto *wrynose*) |
| BSP | meta-tegra `wrynose` = **NVIDIA Jetson Linux R39.2.1 / JetPack 7.2.1** |
| Kernel | `linux-noble-nvidia-tegra` 6.8 |
| Module | Jetson Orin NX 16GB, P3767-0000 (board SKU `699-13767-0000-303`) |
| Rootfs | NVMe (`nvme0n1p1`), boot firmware in the module QSPI |

The layer does not modify Torizon, meta-tegra or OE-Core. Everything Helium-specific lives here, and
the build uses the stock Torizon 8 NVIDIA manifest.

## What the layer does

- **Machine** (`conf/machine/helium-orin-nx.conf`): based on meta-tegra `orin-nx.inc`, with these changes:
  - ODMDATA `gbe-uphy-config-9`. PCIe C9 x1 goes to the LAN7430 (Ethernet 2).
  - Pinmux, GPIO and pad-voltage BCTs from PCB Arts, generated by them from `helium_dp.xlsm`.
  - Ethernet 1 driver (`nv-kernel-module-r8168`) and the Helium peripheral modules: `lan743x`, `rtc-ds1307`,
    `inv-icm42600-i2c`, `atmel-sha204a`.
- **Torizon hook** (`conf/machine/include/helium-orin-nx.inc`): reuses Torizon's
  `jetson-orin-nano-devkit-nvme.inc` unchanged.
- **BCTs** (`recipes-bsp/tegra-binaries`): the PCB Arts files are stored unmodified as `orin_nx_hdmi_a03-*`. They are
  installed as `tegra234-mb1-bct-{pinmux,gpio,padvoltage}-p3767-helium.dtsi`, because the tegraflash packager only
  copies `tegra234-*` BCTs. The MB2 misc BCT is patched so that MB2 does not read a carrier EEPROM (Helium has none).
- **Device tree** (`recipes-kernel/nvidia-kernel-oot`): the stock `tegra234-p3768-0000+p3767-0000-nv-super.dtb` with
  `tegra234-p3768-0000+p3767-0000-helium-overlay.dts` merged in at build time, giving
  `tegra234-p3768-0000+p3767-0000-helium.dtb`. Torizon's UEFI boots the DTB from the OSTree deployment, so the
  carrier changes must be part of the DTB itself. The overlay:
  - disables the FUSB301 (not fitted) and the SD card controller (no slot);
  - sets the USB-C port to `otg` with default role `peripheral`;
  - adds the MCP7940 RTC on I2C1;
  - configures PCIe C7 and C9 as x1 for `gbe-uphy-config-9`.
- **Kernel config** (`recipes-kernel/linux/files/helium.cfg`): LAN743X, MCP7940 RTC, ICM-42670 IMU, ATSHA204A,
  WWAN modems.

## Build

Requirements:
- An x86_64 Linux host with Docker, `repo` and git.
- About 150 GB of free disk.
- A first build takes several hours.

Builds run inside the Torizon `crops` container. Nothing else needs to be installed on the host.

```bash
mkdir helium-torizon8 && cd helium-torizon8
repo init -u https://github.com/torizon/manifest -b wrynose-8.x.y -m torizon/nvidia/release.xml
repo sync -j8
git clone https://github.com/EstebanSannin/meta-helium.git layers/meta-helium
layers/meta-helium/scripts/bitbake.sh torizon-docker
```

`scripts/bitbake.sh` runs bitbake in `torizon/crops:wrynose-8.x.y`, using `build-helium/` as the build directory.
On the first run it generates the build configuration with `scripts/setup-build.sh`. That script:

1. Runs Torizon's `setup-environment` for `jetson-orin-nano-devkit-nvme`, the closest stock machine. Torizon only
   accepts machines listed in `meta-torizon-bsp/scripts/lib/machines.conf`.
2. Switches `MACHINE` to `helium-orin-nx` in `build-helium/conf/auto.conf`.
3. Adds `layers/meta-helium` to `EXTRALAYERS` in `build-helium/conf/bblayers.conf`.
4. Works around a Torizon 8 issue: `setup-environment-nvidia` lists `meta-security` in both `BASELAYERS` and
   `BSPLAYERS`. Bitbake then stops with *"Found duplicated BBFILE_COLLECTIONS 'security'"*, so the
   `BSPLAYERS` copy is removed.

Set `HELIUM_RECONFIGURE=1` to regenerate the configuration. Any bitbake arguments can be passed, for example
`scripts/bitbake.sh -e torizon-docker` or `scripts/bitbake.sh -c cleansstate nvidia-kernel-oot-dtb`.

Output:

```
build-helium/deploy/images/helium-orin-nx/torizon-docker-helium-orin-nx.tegraflash-tar.zst   (~480 MB)
```

Tested with these `torizon/nvidia/release.xml` revisions:

| Layer | Revision |
|---|---|
| meta-torizon | `a29b96f` |
| meta-torizon-bsp | `4a7e3cb` |
| meta-tegra | `2e37d167` |
| openembedded-core | `8830751579` |

## Flash

Requirements on the flashing host (x86_64 Linux, root access):

```bash
sudo apt install -y device-tree-compiler bmap-tools libxml2-utils gdisk udisks2 zstd python3
```

`initrd-flash` stops with *"ERR: 'dtc' command not found"* if `device-tree-compiler` is missing.

1. **Extract** the package on an ext4 filesystem:

   ```bash
   mkdir flash-helium && tar -I zstd -xf torizon-docker-helium-orin-nx.tegraflash-tar.zst -C flash-helium
   ```

2. **Recovery mode.** Connect the Helium USB-C to the host, then power-cycle the Helium (unplug and re-plug DC).
   With USB-C connected to a host at power-on, the Helium enters recovery automatically.
   - From a running Linux on the board, `sudo reboot forced-recovery` also works.
   - The LED is **blue** in recovery and **turquoise** when running normally.
   - Check with `lsusb`: `0955:7323 NVIDIA Corp. APX` is Orin NX 16GB.

3. **Flash** the boot firmware (QSPI) and the NVMe:

   ```bash
   cd flash-helium && sudo ./initrd-flash 2>&1 | tee helium-flash.log
   ```

   It takes about 3–4 minutes. The NVMe shows up on the host as USB storage during step 4, and the run ends with
   `Final status: SUCCESS`. Host-side and device-side logs are left in `flash-helium/`.

4. **Unplug USB-C** before the next power cycle, otherwise the Helium starts in recovery again.

5. **First login**: `ssh torizon@<ip>` with password `torizon`. Torizon forces a password change. The hostname is
   `helium-orin-nx`.

To go back to the PCB Arts image, use their package
(`https://static.pcb-arts.com/helium/orin_generic_v36.5.0_helium_2026-05-19.extractor.sh`) and follow their
documentation: `l4t_initrd_flash.sh … jetson-orin-nano-devkit-super-nvme internal`.

## Status

Tested on a Helium HOX2 on 2026-10-15.

| Area | Status |
|---|---|
| Boot chain (QSPI firmware, Torizon UEFI, OSTree kernel and DTB, NVMe rootfs) | ✅ |
| Ethernet 2: LAN7430 on PCIe C9 (`lan743x`, `ethernet1`) | ✅ 1 Gb/s, DHCP |
| Ethernet 1: RTL8111 on PCIe C8 (`nv-kernel-module-r8168`, `ethernet0`) | ✅ 1 Gb/s full duplex, DHCP, iperf3 941 Mbit/s both directions |
| Ethernet names | ✅ `helium-net-names` pins `ethernet0` (port 1) and `ethernet1` (port 2) by PCIe path, matching Torizon's NetworkManager profiles. Without it the kernel's `eth0`/`eth1` swap between boots |
| NVMe (PCIe C4) | ✅ read 915 MB/s, write 2.0 GB/s; 10-minute random read/write stress without errors |
| USB-C | ✅ default role `device`. Switch with `echo host > /sys/class/usb_role/usb2-0-role-switch/role` |
| RTC MCP7940 (`rtc-ds1307`, `/dev/rtc2`) | ⚠️ driver bound, but the time is invalid until it has been set once (`hwclock -w`). Keeping time needs the coin cell (not fitted from the factory) |
| CAN (`mttcan`) | ✅ interface present |
| GPU (`nvgpu`) and Docker `nvidia` runtime | ✅ present. CUDA workloads not tested yet |
| IMU ICM-42670-P (I2C1 0x69) | ✅ answers, WHO_AM_I `0x67`. ⏳ no device-tree node, so no driver bound |
| ATSHA204A (I2C1 0x64) | ⚠️ answers; device-tree node present. The `atmel-sha204a` driver refuses the chip because its configuration and OTP zones are unlocked (factory state). Locking is permanent, so it is left to the product's provisioning |
| GMSL2 MAX96724 (CAM_I2C = i2c-2, 0x27) | ✅ answers, ID `0xA2`, PoC on at 12 V (PCB Arts defaults). ✅ test pattern captured over MIPI CSI with V4L2 (`HELIUM_CAMERA_TPG = "1"`, see below). ⏳ no camera driver |
| Fan | ✅ PAC.06 output-high in the MB1 pinmux, `helium-fan-enable.service` holds the line, PCB Arts' `nvfancontrol` profile. 2650–2850 RPM at idle. |
| LAN743X EEPROM MAC setup (PCB Arts first-boot script) | ⏳ not ported |
| CPU clock | ✅ up to 1.5 GHz in the default 40 W mode (NVIDIA profile), 2.0 GHz in MAXN_SUPER (`nvpmodel -m 0`) |
| OP-TEE | ✅ runs over SMC (`/dev/tee0`); the `arm_ffa` message is informational. fTPM needs NVIDIA EKB provisioning |

### Device-tree updates

The Helium DTB ships in the OSTree deployment, so OS updates and rollbacks
carry device-tree changes. UEFI applies its overlays (memory carveouts, OP-TEE)
and fixups to the deployed DTB as it does to the flashed one.

## Camera path test without a camera

`HELIUM_CAMERA_TPG = "1"` in `local.conf` merges
`tegra234-p3767-helium-camera-tpg-overlay.dts` into the Helium DTB and installs
`helium-max96724-tpg`, a tegracam driver that makes the MAX96724 output its
internal video pattern (1920x1080 RGB888, 30 fps) over MIPI CSI. It claims the
deserializer, so leave it off when a real camera driver is used.

```
docker run --rm --privileged -v /dev:/dev -v /tmp:/out debian:trixie-slim sh -c \
  'apt-get update && apt-get install -y v4l-utils && \
   v4l2-ctl -d /dev/video0 --stream-mmap --stream-count=10 --stream-to=/out/frame.raw'
```

Each frame is 1920x1080 RGBA (`AB24`, 8 294 400 bytes). Module parameters:
`pattern` (0 checkerboard, 1 gradient), `quad_2lane`, `csi_port`, `lane_map`,
`lane_polarity`, `dpll_mbps` (see `modinfo helium_max96724_tpg`).

The driver runs the deserializer in 4x2 mode (2 lanes per PHY, every PHY
carries the pattern) and the DT captures 2 lanes on Tegra CSI C. Findings:

- Only Tegra CSI C and D receive data; CSI A and B see nothing in any mode.
- The upstream staging max96712 sequence leaves pipe 0 routed to PHY0, which is
  not a port master in 2x4 mode, so nothing leaves the chip. The routing (pipe
  to PHY, VC/DT maps for pixels and FS/FE) comes from ADI's maxim-serdes
  max96724 driver.
- 4 lanes (deserializer port B → Tegra CSI C x4) still fails: frames arrive
  with payload CRC errors (`CSI_FAULT_PD_CRC_ERR`) at every lane map and rate
  tried.

## Debugging without the H-DBG adapter

The debug UART (`ttyTCU0`, 115200 8N1) is only reachable through PCB Arts' USB-C debugger (`H-DBG`). Without it:
- watch the `initrd-flash` logs on the host;
- connect DisplayPort over a USB-C dock;
- read `/sys/fs/pstore` after a crash;
- use SSH once userspace is up.

## Provenance

- `recipes-bsp/tegra-binaries/files/orin_nx_hdmi_a03-*.dtsi`: unmodified copies from PCB Arts' public JetPack
  36.5.0 package (`orin_generic_v36.5.0_helium_2026-05-19`, `Linux_for_Tegra/bootloader/generic/BCT/`). NVIDIA's
  stock R36.5 and R39.2.1 pinmux formats are identical, so they apply unchanged on R39.
- The device-tree overlay was reconstructed from the live device tree of a Helium running the PCB Arts image, plus
  their `301-generic-helium.dtbo`.
